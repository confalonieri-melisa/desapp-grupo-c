# Data Model: Mercado P2P de Tokens de Jugadores — Backend

## Existing entities reused

### `users`

- `id` UUID primary key.
- `role` identifies `INVESTOR` or `SUPERUSER`.
- `credit_balance` numeric(12,2), never negative.
- The `SUPERUSER` row remains the central pool for `POST /api/orders/buy`.

### `token_holdings`

- Existing unique key `(user_id, player_id)` remains the source of total token
  holdings.
- `quantity` remains an integer with `quantity >= 0`.
- No `reserved_quantity` column is added. Available quantity is derived as:
  `token_holdings.quantity - SUM(p2p_offers.reserved_quantity WHERE seller_id = user_id AND player_id = ... AND status = 'OPEN')`.
- The seller's total holding does not change when publishing an offer. On
  fill, the reserved amount is transferred by reducing the seller holding and
  increasing/upserting the buyer holding. On cancellation, only the offer
  reservation is released.

### `player_quotes`

- Existing quote snapshot is referenced by `quote_id`.
- `quote_value` is captured at scale 2 when the offer is published and is not
  re-read at purchase time.

### `market_operations`

- Existing `BUY`/`SELL` type constraint is preserved.
- A P2P fill is recorded as one `SELL` operation for the seller, with a new
  nullable `counterparty_user_id` pointing to the buyer and a nullable
  `offer_id` pointing to the P2P offer.
- Existing pool buys continue to use `BUY`; the disabled pool sell route does
  not create an operation.
- The operation keeps `quote_value`, `quantity`, `total`, `unit`,
  `correlation_id`, and `created_at` as immutable snapshots.

### `financial_audit_records`

- Existing append-only audit is reused.
- Make `operation_id` nullable and add nullable `offer_id` FK to `p2p_offers`.
  Existing `TOKEN_BUY`/`TOKEN_SELL` rows keep `operation_id` and no offer.
  `P2P_OFFER_PUBLISHED` and `P2P_OFFER_CANCELLED` use `offer_id` and no
  operation. `P2P_OFFER_SOLD` uses both `offer_id` and `operation_id`.
- Add actions `P2P_OFFER_PUBLISHED`, `P2P_OFFER_SOLD`, and
  `P2P_OFFER_CANCELLED`, or widen the existing action constraint while keeping
  the append-only audit semantics.
- Add a check constraint matching the action/reference combinations above;
  every state transition has one auditable row in the same transaction.

## New table: `p2p_offers`

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key, generated by the database/application |
| `seller_id` | UUID | Required FK to `users`; must be an investor at service level |
| `buyer_id` | UUID | Nullable FK to `users`; set only on `SOLD` |
| `player_id` | UUID | Required FK to `players` |
| `quote_id` | UUID | Required FK to `player_quotes` |
| `quantity` | integer | Required, `> 0` |
| `reserved_quantity` | integer | Required, `>= 0`, `<= quantity` |
| `unit_price` | numeric(10,2) | Required, `>= 0` |
| `total` | numeric(12,2) | Required, `> 0`, equals `unit_price * quantity` |
| `status` | varchar(12) | Required enum: `OPEN`, `SOLD`, `CANCELLED` |
| `created_at` | timestamptz | Required |
| `closed_at` | timestamptz | Nullable; set on fill/cancel |

Constraints and indexes:

- `status = 'OPEN'` implies `reserved_quantity = quantity` and `buyer_id IS NULL`.
- `status IN ('SOLD','CANCELLED')` implies `reserved_quantity = 0` and
  `closed_at IS NOT NULL`.
- `status = 'SOLD'` implies `buyer_id IS NOT NULL` and `buyer_id <> seller_id`.
- `status = 'CANCELLED'` implies `buyer_id IS NULL`.
- Index `(status, player_id, created_at, id)` supports the open-offer query.
- Index `(seller_id, player_id, status)` supports reservation aggregation and
  seller ownership checks.
- Index `(buyer_id)` is optional and only added if portfolio/history queries
  need it; it is not required by the MVP.

## New table: `idempotency_keys`

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Required FK to `users` |
| `idempotency_key` | varchar(255) | Required, trimmed non-empty |
| `method` | varchar(10) | Required HTTP method |
| `path` | varchar(255) | Required canonical route |
| `request_hash` | varchar(128) | Required hash of normalized payload |
| `response_status` | integer | Nullable until the transaction completes |
| `response_body` | jsonb | Nullable until the transaction completes |
| `created_at` | timestamptz | Required |
| `completed_at` | timestamptz | Nullable until completion |

Constraints and indexes:

- Unique `(user_id, idempotency_key)`.
- `response_status` and `response_body` are both null or both non-null.
- A same-key request with a different method, path, or hash returns `409`.
- Authentication and request-shape validation happen before creating a row;
  only authenticated, well-formed mutating requests are idempotency records.

## State transitions

```text
OPEN ──purchase──> SOLD
OPEN ──cancel────> CANCELLED
SOLD and CANCELLED are terminal.
```

The transition is performed with a conditional update or a locked row. A
failed conditional update is a business `409` and must not touch balances,
holdings, operations, audits, or idempotency effects beyond replay metadata.
